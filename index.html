01

The Allocation Problem

Every organisation has costs that don't belong to just one department — the IT team supports everyone, Facilities maintains the whole building, Finance processes payroll for all staff. These are shared costs, and deciding how much each service line should bear is not a trivial accounting question.

The traditional approach is simple step-down allocation — costs trickle down a fixed hierarchy, one level at a time. It is fast to implement. But it ignores a fundamental reality: shared services support each other. IT supports Finance. Finance supports HR. HR supports IT. In step-down, circular relationships are either ignored or broken by a fixed ordering, producing an approximation that cannot be audited to its true source.

CharacteristicStep-DownFull Reciprocal (this model)
Service-to-service flowsOne direction only — fixed hierarchyCircular — fully resolved
Circular relationshipsIgnored or approximated by orderingExact — Leontief iteration
AuditabilityLimited — allocation sequence mattersComplete — every dollar traceable
End-to-end balanceDependent on rule designEnforced — RC01–RC06 checks
Model change required on reorderYesNo — network resolves dynamically

The circular dependency. IT pools charge Facilities for system support. Facilities pools charge IT for floor space and utilities. In step-down, one of these flows must be cut — creating a known inaccuracy. Full reciprocal allocation resolves both simultaneously with no approximation.

02

Design Principles

The module implements Activity Based Costing (ABC) with full reciprocal apportionment. Costs flow from GL accounts into Cost Pools, from Pools into Activities, and from Activities into Service Lines — three conceptual levels, each with its own driver logic.

Where those levels have circular relationships, the model resolves them using the Leontief Input-Output model — the same framework used in macroeconomic analysis to model how industries depend on each other. A cost pool can apportion to another pool, which apportions back to the first; the iteration runs until the numbers stop changing. The result is a mathematically exact answer, not an approximation.

The Two-Layer Architecture

The engine splits cleanly across two technologies:

LayerTechnologyWhen it runsStages handled
Live apportionment TM1 Rules Continuously — recalculates on any data change Stage 1, Stage 2, Stage 3
Reciprocal iteration Python ETL On demand — run each period after data load Stage 1b, Stage 2b

TM1 rules are declarative and cannot loop — they are ideal for stages where the calculation is a direct formula applied to each intersection. Python handles the iterative stages where circular flows require repeated passes to converge. The two layers are cleanly separated: Python writes the settled amounts back to TM1 and TM1 rules read from them, giving a live view of the post-reciprocal result without re-running Python.

Everything is code. All TM1 objects — dimensions, cubes, rules, views, TI processes — are defined in source files in this repository and deployed by the build scripts. Git is the source of truth. There is no manual Architect work. A git diff shows exactly what changed between environments.

03

The Apportionment Chain

Costs flow through five stages. The three TM1 rules stages are live at all times; the two Python iteration stages run each period to resolve circular pool and activity flows.

Each config cube feeds its stage with the driver assumptions for that level of allocation. The two Python stages write their settled amounts back to TM1; subsequent TM1 rules stages read from those settled values rather than the raw pool totals.

04

Stage 1 — Account → Pool

Every GL account is classified as one of three Apportionment Types in CST Account Config:

Apportionment TypeBehaviour
IndirectAccount amount apportioned to one or more Cost Pools via Driver %. Enters the apportionment chain at Stage 1.
DirectAccount bypasses the pool and activity chain. Splits directly to Service Lines via Direct Service Line %. Enters the P&L at Stage 3 output.
ExcludedAccount excluded from apportionment entirely. Does not appear in the P&L output.

How Indirect Accounts Apportion

For Indirect accounts, CST Account Config stores a Driver % for each account-pool pairing. These percentages represent how the account's cost should be split across the pools it feeds — and they must sum to 100% for each account.

The TM1 rule is straightforward:

# CST Account to Pool Apportionment
Apportioned Amount = GL Amount × Driver %

Because it is a TM1 rule, it recalculates instantly whenever the GL amount or the Driver % changes. No TI process, no manual refresh. The Account to Pool Apportionment cube always reflects current data.

Account Config is maintained manually. Pool assignments and Apportionment Type reflect model design decisions — which overhead accounts belong to which pools — and are set infrequently. They are stored in TM1 and maintained via a PAW websheet. They are not loaded from CSV.

05

Stage 1b — Pool ↔ Pool Reciprocal

Cost pools serve each other. The IT pool charges Facilities for system support. The Facilities pool charges IT for floor space. In step-down, one of these flows is cut. In this model, both are fully resolved.

Stage 1b is the reciprocal pool solver. Python reads the pool totals from Stage 1, reads the inter-pool driver values from CST Pool to Pool Config, and iterates until the settled amounts stop changing.

Driver Values and How They Work

Driver values are raw operational volumes — not pre-calculated percentages. For each source pool → destination pool pair, the config stores the raw volume of the destination pool's consumption of the source pool's service. Examples: tickets raised (for IT), floor area in sqm (for Facilities), headcount (for HR).

Python normalises these at runtime: each source pool's total outgoing volume becomes 100%, and each destination's driver value becomes its fractional share. This means the percentages always reflect the current period's actual volumes, without any pre-calculation step.

Driver values are loaded from CSV, not entered manually. They are raw operational volumes sourced from HR systems, facilities management, and other operational data — refreshed each period via ETL. The Active flag in Pool to Pool Config defines which source → destination pairs are live; normalisation runs only over Active=1 pairs.

The Solver

The iteration runs on pool-level aggregates (not cost centre level). Each pass:

  1. For each source pool: redistribute its current balance to destination pools using normalised driver percentages
  2. Update each destination pool's balance (base amount + received allocations − outgoing allocations)
  3. Compute max absolute change across all pools
  4. Repeat until max change < 0.01 (typically ~11 iterations)

Convergence is dynamic — the loop breaks when the tolerance is met. The --max-iter 100 flag is a safety cap only and is never reached in practice.

The Input Sentinel Pattern

All coded CST dimensions carry an Input element at weight 0 under their consolidation. It acts as a reserved slot for storing scalar values that belong to the dimension logically but have no natural counterpart dimension. In Stage 1b:

# Driver Value stored at Cost Centre = "Input"
CST Pool to Pool Config[period, version, CP01, CP03, Input, Driver Value] = 4200

# Redistribution % stored at Cost Pool Dest = "Input"
CST Pool to Pool Config[period, version, CP01, Input, Input, Redistribution %] = 85

After convergence, Python writes the Settled Amount for each pool back to CST Pool to Pool Config at Cost Pool Dest = Input. TM1 rules in Stage 2 read from this intersection to get the post-reciprocal pool balances.

Cost Centre Split-Back

The reciprocal iteration runs at pool aggregate level for speed. After convergence, costs are split back to the individual Cost Centre level using the Stage 1 ratio:

ratio = CC Stage 1 amount / Pool Stage 1 total
CC settled amount = Pool settled amount × ratio

This preserves the Cost Centre proportions from Stage 1 exactly, applying the same reciprocal adjustment uniformly across all Cost Centres within a pool.

06

Stage 2 — Pool → Activity

With pool-to-pool flows resolved, Stage 2 distributes each pool's settled amount across the Activities it supports. Each pool can feed multiple activities; the split is driven by Driver % Share in CST Pool Config.

The driver at this stage answers a different question from Stage 1b: not "how much does this pool serve another pool?" but "how do the downstream activities actually consume this pool's service?" A Facilities pool's floor-area driver will assign different percentages when splitting to activities than when splitting pool-to-pool — because the activities occupy different proportions of the building than the pools do.

Each stage has its own driver values. The same operational metric (e.g., FLOORSPACE) will carry different numbers at each stage because the question changes: Stage 1b asks how pools consume other pools; Stage 2 asks how activities consume pools; Stage 3 asks how service lines consume activities. Same driver type, different volumes, different cost object.

The TM1 rule reads the Stage 1b Settled Amount and applies the Driver % Share:

# CST Pool to Activity Apportionment
Apportioned Amount = P2A Settled Amount × Driver % Share

Because Stage 2 is a TM1 rule reading from a settled amount written by Stage 1b Python, the Activity apportionment updates immediately whenever Stage 1b is re-run — no manual refresh needed for subsequent stages.

07

Stage 2b — Activity ↔ Activity Reciprocal

Just as cost pools can serve each other, activities can support each other. A Training activity may serve a Finance activity, which in turn provides support back to Training. Stage 2b resolves these circular activity flows using the same Python iteration solver as Stage 1b.

Stage 1bStage 2b
ObjectCost Pools (CP01–CP09)Activities (A01–A11)
Config cubeCST Pool to Pool ConfigCST Activity to Activity Config
Driver valuesRaw volumes, CSV loadedRaw volumes, CSV loaded
ConvergenceMax change < 0.01Max change < 0.01
Settled amount targetP2A Settled Amount in Pool ConfigA2SL Settled Amount in Activity Config

After convergence, Python writes the settled activity amounts to CST Activity Config at Activity Dest = Input. Stage 3 TM1 rules read from these values to produce the final Service Line apportionment.

08

Stage 3 — Activity → Service Line

Stage 3 is the final distribution — each activity's settled amount splits to Service Lines using Driver % Share stored in CST Activity Config. The driver at this stage answers how each service line consumes each activity's output.

Direct cost accounts (Apportionment Type = Direct, assigned in Stage 1) also arrive at Stage 3 via their direct Service Line percentages, bypassing the pool and activity chain entirely. Both indirect and direct costs land in CST Activity to Service Line Apportionment, which feeds the P&L report.

# CST Activity to Service Line Apportionment
Apportioned Amount = A2SL Settled Amount × Driver % Share
# Direct costs bypass pools/activities:
Direct Amount      = GL Amount × Direct Service Line %

The CST Profit and Loss Report cube aggregates all stages — pre-apportionment GL, each apportionment stage, and the final post-apportionment view — across Period, Version, Account, Service Line, Cost Centre, and Stage dimensions. Every figure traces back to its source.

End-to-end balance. The total that enters at Stage 1 (all Indirect overhead accounts) must equal the total that exits at Stage 3 (all Service Line allocations). The RC06 reconciliation check enforces this. If it fails, nothing leaves the model until the variance is found and corrected.

The Input Sentinel Pattern

Input sentinel. Every coded CST dimension carries an Input element at weight 0 under its consolidation. It provides a reserved intersection for storing scalar values that belong to a dimension contextually but have no natural counterpart on another dimension axis — driver values, redistribution percentages, base amounts, and settled balances all use this pattern. Because Input carries weight 0, it never rolls up into any consolidation, preventing double-counting.

Naming Conventions

All objects use the CST prefix. Cubes follow the flow naming convention: CST [Source] to [Destination] Apportionment. Dimension elements use a two-part pattern: element = code (CP01), alias = code + description (CP01 Facilities). Destination dimensions are exact mirrors of their source — same elements, same aliases.

10

Validation Gate

Before Stage 1b runs, Python executes six gate checks against the TM1 model. A FAIL on any check blocks the apportionment; a WARNING allows it to proceed with a visible alert that results are interim.

CheckWhat it validatesStatus on failure
VAL01Pool Config — all pools have driver percentage shares configuredFAIL
VAL02Activity Config — all activities have input volumes configuredFAIL
VAL03Driver SQL vs TM1 spot-check — loaded values match SQL source totals within toleranceFAIL (skipped with WARNING if SQL unavailable)
VAL04Account Config — all overhead accounts have pool assignments (Driver % sums to 100)FAIL
VAL05Account Config — all Direct accounts have Direct % configured (sums to 100)FAIL
VAL06Account Config — no accounts with blank Apportionment TypeFAIL

Pool-to-pool and activity-to-activity driver completeness raises a WARNING not a FAIL — missing reciprocal config is valid if those pairs are simply not configured (the pair is skipped, not errored).

Override with care. Running python3 etl/run_apportionment.py --force bypasses FAIL gates and proceeds with whatever data is present. Results will be incomplete. Only use --force for exploratory runs with known-incomplete config data.

VAL check results are written to CST Apportionment Reconciliation at each run. They are always visible in PAW alongside the RC checks.

11

Reconciliation Checks

Six reconciliation checks run as always-live TM1 rules in CST Apportionment Reconciliation. They fire automatically whenever any input data changes — no separate process to run. Status is PASS if ABS(Variance) ≤ 0.01, FAIL otherwise, and NO DATA if the input total is zero.

CheckStageWhat it confirms
RC01Stage 1GL Amount at Input cost pool = Apportioned Amount at Total Cost Pools
RC02Stage 1bPool Base Amount = Pool Final Balance after reciprocal (net flow = 0)
RC03Stage 2Amount at Input activity = Apportioned Amount at Total Activities
RC04Stage 2bActivity Base Amount = Activity Final Balance after reciprocal
RC05Stage 3Amount at Input service line = Apportioned Amount at Total Service Lines
RC06End-to-endGL Input total = Post Apportionment at Total Service Lines

RC06 is the critical check. It confirms that every dollar of overhead that entered the model at Stage 1 has been fully allocated to a Service Line by Stage 3, with no leakage and no duplication. If RC06 fails, the P&L output cannot be used.

RC02 and RC04 validate the reciprocal stages specifically: after Python iteration, the net flow in and out of each pool (or activity) must be zero. These checks are what confirm that the Leontief solver has converged correctly and the settled amounts are mathematically consistent.

Building and Running

1. Clone and install

git clone https://github.com/JDLovering/tm1_apportionment.git
cd tm1_apportionment
pip install -r requirements.txt

2. Configure connection

Copy the example env file and edit with your TM1 server address and credentials:

cp .env.example .env
# edit .env with TM1_ADDRESS, TM1_PORT, TM1_DATABASE, credentials

Alternatively, copy and edit config.example.py → config.py. The .env file takes precedence. Never commit either file — both are in .gitignore.

3. Deploy the model

python3 model_builder/deploy.py

Deploys all dimensions, cubes, rules, subsets, views, and TI processes from the JSON definitions in model_builder/tm1_objects/. The target server is read from the connection config.

4. Load sample data

python3 load_csv_data.py
# or generate the SQLite test database first:
python3 model_builder/create_test_db.py
python3 etl/load_gl.py --version Budget
python3 etl/load_drivers.py --version Budget

5. Validate and run

python3 etl/val_checks.py --version Budget
python3 etl/run_apportionment.py --version Budget

# Single period:
python3 etl/run_apportionment.py --period 2026-04 --version Budget

# Override FAIL gates (incomplete data, exploratory):
python3 etl/run_apportionment.py --version Budget --force

6. PAW-triggered ETL

./start_poller.sh
# Required for TI-triggered ETL from Planning Analytics Workspace

Rebuild / Teardown

python3 model_builder/cleanup_cst_model.py   # safely removes all CST objects
python3 model_builder/build_cst_model.py     # full rebuild
